# AI 辅助前端的界面契约：让生成结果可验证、可维护

> 把“做得高级一点”转换为设计 token、组件状态、响应式规则、可访问性和验收门槛，让 AI 生成的界面不再依赖主观感觉。

## 为什么只写 PRD 还不够

PRD 能说明用户要完成什么任务，却通常不会定义界面应该如何保持一致。例如，“创建一个专业的结账页”没有回答这些问题：

- 标题、正文和辅助文字分别使用什么字号与行高？
- 输入框处于默认、聚焦、错误、禁用和加载状态时如何表现？
- 组件在 320px、768px 和桌面宽度下如何重排？
- 键盘焦点、错误提示、减少动画偏好如何处理？
- 什么证据能够证明页面已经达到可发布标准？

如果这些信息没有写下来，AI 会用训练数据中的常见模式补全空白。单个页面可能看起来合理，但页面之间的间距、状态和交互会逐渐漂移。解决办法是在 PRD 和代码之间增加一份“界面契约”。

## 界面契约包含什么

界面契约是一份可以由设计师、开发者和 AI 编码工具共同读取的约束文档。它至少包含六类信息。

### 1. 设计 token

不要只写“蓝色按钮”或“较大的间距”。定义可复用的名字和值：

```yaml
tokens:
  color:
    action: "#2563EB"
    text: "#111827"
    muted: "#6B7280"
    danger: "#DC2626"
  spacing:
    xs: 4
    sm: 8
    md: 16
    lg: 24
  radius:
    control: 8
    panel: 12
```

生成代码时只能引用 token，不允许临时添加相近颜色或随意的像素值。这样可以减少重复和视觉漂移。

### 2. 完整的组件状态

每个交互组件都应该列出它支持的状态。一个按钮至少要考虑：

- 默认、悬停、按下和键盘聚焦
- 禁用
- 提交中
- 成功或失败后的反馈

表单还需要空值、格式错误、服务端错误和只读状态。把状态写成清单，比要求 AI “处理所有边界情况”更容易检查。

### 3. 响应式行为

界面契约不应只提供几个截图。它需要解释布局在宽度变化时的规则：

- 哪些区域可以换行？
- 哪些操作需要折叠进菜单？
- 表格何时转为卡片或允许横向滚动？
- 内容最大宽度是多少？
- 触控目标是否仍然足够大？

优先描述行为，而不是为每个设备复制一套固定尺寸。

### 4. 可访问性

把可访问性写进完成条件，而不是发布前的补丁。至少检查：

- 所有功能能否只用键盘完成
- 焦点是否清晰可见并按合理顺序移动
- 表单控件是否有程序可识别的标签
- 错误信息是否与对应字段关联
- 文本与背景是否达到所需对比度
- 动画是否尊重 `prefers-reduced-motion`

### 5. 动画约束

动画应该说明目的、持续时间、缓动方式和中断行为。例如，页面过渡可以帮助用户理解层级变化，但不应该阻止操作。为进入、退出、反馈和加载分别定义少量 token，并为减少动画模式提供替代方案。

### 6. 生产验收门槛

“看起来不错”无法重复验证。可以把完成条件写成二元检查项：

- 关键组件的所有状态均可访问
- 320px 到桌面宽度无内容溢出
- 键盘流程通过
- 加载、空状态和错误状态均有测试
- 未出现契约之外的新颜色、间距或圆角
- 核心页面通过截图差异检查
- 控制台无错误，链接和表单均可用

## 在 AI 编码流程中如何使用

一个可靠的流程可以分成五步。

1. **先写契约，再生成页面。** 把契约和 PRD 一起提供给 AI，明确冲突时以契约为准。
2. **按组件和状态拆分任务。** 不要一次生成整个产品；先完成基础组件，再组合页面。
3. **要求引用约束。** 让 AI 在实现说明中指出使用了哪些 token、状态和响应式规则。
4. **自动检查确定性规则。** 用 lint、类型检查、组件测试、可访问性测试和多视口截图验证可以机器判断的内容。
5. **人工检查体验。** 设计师或开发者仍需验证视觉层级、内容清晰度、交互节奏和异常场景。

## 一个可复制的最小模板

```yaml
page:
  goal: ""
  primary_action: ""
tokens:
  color: {}
  spacing: {}
  typography: {}
components:
  button:
    states: [default, hover, focus, disabled, loading]
responsive:
  mobile: ""
  tablet: ""
  desktop: ""
accessibility:
  keyboard: true
  visible_focus: true
  reduced_motion: true
acceptance:
  - "所有状态均已实现"
  - "关键视口无溢出"
  - "键盘流程通过"
  - "错误与空状态已测试"
```

模板不需要一开始就很长。真正重要的是：每条规则都能被实现，每个完成条件都能被验证，变更时契约与代码同步更新。
